# Конспект: Git от нуля до pull request

## Часть 1. Зачем нужны cистемы контроля версий

**Система контроля версий (VCS, Version Control System)** — программа, которая записывает изменения файлов. Благодаря ей можно вернуться к любой прошлой версии и работать над проектом вместе с другими людьми. Аналогия: «история версий» в Google Документах или сохранения в компьютерной игре, только для файлов проекта.

### Какие проблемы были без VCS

1. **Версии вручную.** Копии папок вида `project_final_v2_REAL(1).zip`. Через неделю непонятно, чем отличаются копии и какая из них последняя рабочая. Каждая копия занимает место целиком, даже если изменилась одна строка.
2. **Два человека правят один файл.** Аня и Борис скачали один файл, каждый внёс правки. Борис сохранил позже, и его версия заменила файл в общей папке: правки Ани пропали, никто этого не заметил. Нужна система, которая соединит правки или честно скажет, что они пересекаются. Такое пересечение называется **конфликтом (conflict)**.
3. **Переписка прямо в коде.** Журнал изменений, пометки «НЕ ПРАВИТЬ!», `TODO` (пометка о незаконченной работе), `HACK` (временный «костыль»). Комментарии быстро устаревают, не защищают от перезаписи и засоряют код.

### Что умеет VCS

- **История** — помнит каждую сохранённую версию.
- **Откат** — возвращает файлы к нужной версии.
- **Авторство** — показывает, кто, когда и зачем изменил.
- **Совместная работа** — объединяет правки разных людей.

### Пример масштаба: Windows

Исходный код (source code) — обычные текстовые файлы, из которых собирается программа. До 2017 года код Windows лежал в собственной системе Microsoft — Source Depot (более 40 отдельных хранилищ), потом команда перешла на git. Размер git-репозитория Windows — около 300 ГБ, в проекте около 3,5 млн файлов. Вывод: git справляется даже с одним из самых больших проектов в мире. Архив исходников Windows XP, утёкший в 2020 году, весил около 43 ГБ.

### Три поколения систем

&#91;embedded content: три поколения систем контроля версий\]

- **Локальные (1970–80-е)**: SCCS (1972), RCS (1982). История хранится на одном компьютере, работать вдвоём неудобно.
- **Централизованные (1990–2000-е)**: CVS (1990), Subversion/SVN (2000). Есть общий сервер со всей историей. Клиент делает **checkout** (получает рабочую копию — файлы последней версии), а командой **commit** отправляет правки по сети, и их сразу видят все. Минус: без сети и сервера нельзя ни сохранить версию, ни посмотреть историю.
- **Распределённые (2005 и далее)**: Git и Mercurial (оба 2005). У каждого разработчика своя полная копия репозитория вместе с историей. **Клонирование (clone)** скачивает не только файлы, но и всю историю. Версии сохраняются офлайн, интернет нужен только для обмена правками. Если сервер пропал, любая копия может его заменить. Общий сервер (GitHub, GitLab) — удобная договорённость, а не требование системы.

### Как появился git

1. Ядро Linux разрабатывают тысячи людей, нужна система, которая выдерживает такой поток правок.
2. Сначала использовали закрытую (проприетарную) программу BitKeeper. В апреле 2005 года бесплатный доступ для сообщества Linux закончился.
3. Линус Торвальдс начал писать собственную систему. Цели: скорость, простое устройство, множество параллельных веток, защита данных от порчи.
4. Первая рабочая версия появилась за считанные дни. Сегодня git — самая популярная VCS в мире. Название «git» — английское сленговое слово; автор шутил, что назвал проект в свою честь.

## Часть 2. Что такое git

**Git** — распределённая система контроля версий (distributed VCS). Это обычная программа на вашем компьютере, как браузер или текстовый редактор. История проекта хранится в папке рядом с файлами. Интернет нужен только для обмена правками с другими. **Git — не сайт**: GitHub и GitLab — отдельные сервисы (см. часть 10).

### Шесть свойств git

| Свойство | Что значит |
| --- | --- |
| Распределённый | У каждого разработчика полная копия проекта вместе с историей |
| Быстрый | Почти все команды работают с файлами на вашем диске и не ждут сервер |
| Надёжный | Целостность (integrity) данных защищена хэшами: повредить историю незаметно нельзя |
| Ветки | Ветка (branch) — отдельная линия работы; пробуете идею, не ломая основной код; создаётся мгновенно |
| Свободный | Open source и бесплатный, лицензия GPL версии 2 |
| Универсальный | Хранит любые файлы, но лучше всего подходит для текста: код, настройки, документация |

### Установка

| Система | Как поставить |
| --- | --- |
| Windows | Установщик Git for Windows с git-scm.com (настройки по умолчанию подойдут) или `winget install --id Git.Git -e` |
| macOS | `git --version` в терминале (система сама предложит инструменты разработчика) или `brew install git` |
| Linux | Ubuntu и Debian: `sudo apt install git`; Fedora: `sudo dnf install git` |

Проверка: `git --version` выводит номер версии, например `git version 2.43.0`. Если номер виден, git установлен.

### Терминал или кнопки

- **CLI** (command line interface) — команды вводят текстом: `git status`. Плюсы: работает везде, видно всё, что происходит.
- **GUI** (graphical user interface) — кнопки в редакторе, например в VS Code. Плюсы: наглядно, меньше шансов ошибиться в синтаксисе.
- Терминал в VS Code открывается клавишами \`Ctrl+\`\` (кавычка на клавише Ё).

### Представиться git (один раз после установки)

```bash
git config --global user.name "Ivan Petrov"
git config --global user.email "ivan@example.com"
git config --global --list   # проверить настройки
```

- `config` — «настроить», `--global` — для всех проектов на этом компьютере, `user.name` — название настройки, значение в кавычках.
- Имя будет подписью автора в каждом коммите. Команда ничего не выводит — это нормально.
- Почта попадает в каждый коммит. GitHub по почте узнаёт, чей это коммит, поэтому используйте ту же почту, что в аккаунте.

## Часть 3. Хеш: отпечаток данных

**Хеш-функция (hash function)** — «коробочка»: на входе любые данные любого размера (слово, файл, фильм), на выходе короткая строка фиксированной длины — отпечаток. Как отпечаток пальца: человек большой, а отпечаток маленький, но по нему человека можно узнать. Из отпечатка нельзя восстановить файл: это дорога в одну сторону.

### Четыре свойства хеша

1. **Одинаковый вход — одинаковый хеш.** Сколько раз ни считай хеш слова «hello», результат один и тот же.
2. **Мелкое изменение — совсем другой хеш.** Поменяли одну букву, и отпечаток не похож на прежний.
3. **Длина всегда одинакова.** Хоть слово, хоть фильм: на выходе строка одной длины.
4. **Назад не восстановить.** По хешу нельзя вернуть данные, можно лишь сравнить.

Раз выходов меньше, чем входов, у разных данных теоретически может совпасть хеш — это **коллизия (collision)**. У хороших функций это практически не случается.

### Живой пример: SHA-1

```bash
$ printf 'hello' | sha1sum
aaf4c61ddcc5e8a2dabede0f3b482cd9aea9434d
$ printf 'Hello' | sha1sum
f7ff9e8b7bb2e09b70935a5d785e0cc5d9d0abf0
$ printf 'hello!' | sha1sum
8f7d88e901a5ad3a05d8cc0de93313fd76028f8c
```

Замена «h» на «H» или добавленный «!» полностью меняют отпечаток. Длина всегда 40 символов (шестнадцатеричные цифры 0–9 и a–f). `sha1sum` есть в Linux; на macOS — `shasum`; в Windows PowerShell — `Get-FileHash`.

### Зачем хеш git

- **Имя для коммита.** Каждому коммиту и файлу git даёт имя — его хеш, не нужно придумывать «версия\_финал\_2».
- **Защита от порчи.** Если содержимое изменится или повредится, хеш не совпадёт, и git это заметит.
- **Быстрое сравнение.** Чтобы понять, изменился ли файл, достаточно сравнить хеши, читать файл целиком не нужно.

Хеш содержимого файла git считает так: `printf 'hello\n' | git hash-object --stdin` даёт `ce013625030ba8dba906f756967f9e9ca394464a`. В списках коммитов видны только первые 7 символов (например `ce01362`) — этого хватает, чтобы однозначно указать на коммит. Современные версии git умеют и более длинный SHA-256.

## Часть 4. Как git устроен внутри

### Снимки, а не разница

- **Дельты (старый подход):** запись только того, что поменялось («в строке 5 заменили слово»). Чтобы получить версию, надо применить все изменения подряд с самого начала.
- **Снимки (подход git):** снимок (snapshot) — «фотография» всех файлов проекта в момент коммита. Версию можно открыть сразу, ничего не накладывая.
- Если файл не менялся, git не копирует его заново, а ссылается на прежнюю версию, поэтому репозиторий не раздувается. Именно поэтому в git быстро переключаться между версиями и ветками.

### Из чего git собирает историю

| Объект | Что это | Что хранит |
| --- | --- | --- |
| blob | содержимое файла | Текст файла, но не его имя. Имя — хеш содержимого |
| tree | дерево, то есть папка | Список: какое имя файла какому blob соответствует, плюс вложенные папки |
| commit | сохранённая версия | Указывает на корневое дерево, автора, сообщение и предыдущий коммит |
| tag | метка | Постоянное имя для важного коммита, например `v1.0` |

Все объекты лежат в скрытой папке `.git` в корне проекта. Запоминать их устройство не нужно, важно знать, что всё построено на хешах.

### Что внутри коммита

- **Хеш** (например `3f2a9c1`) — уникальное имя версии.
- **Автор (author)** — имя и почта из настроек; **дата (date)**; **сообщение (message)** — что и зачем изменили.
- **Родитель (parent)** — предыдущий коммит. По этим ссылкам образуется цепочка истории.
- **Дерево (tree)** — снимок файлов на этот момент.

### Три области

&#91;embedded content: три области git и команды между ними\]

Зачем средняя область? Можно изменить десять файлов, а в один коммит отправить только три, связанных по смыслу. Каждый коммит получается чистым и понятным. Образ для запоминания — семейное фото: рабочая папка — сцена, где люди двигаются и меняются; индекс — вы выбираете, кто попадёт в кадр; репозиторий — готовое фото в альбоме.

### Жизненный цикл файла

&#91;embedded content: жизненный цикл файла: пять состояний\]

| Состояние | Что значит | `git status` | В VS Code |
| --- | --- | --- | --- |
| Untracked | Новый файл лежит в папке, git о нём не знает и в коммит не возьмёт, пока не сделаете `git add` | `Untracked files` | Буква U, имя зелёное |
| Unmodified | Файл сохранён в git и совпадает с последним коммитом: «спокойное» состояние | `nothing to commit, working tree clean` | Не показывается в списке |
| Modified | Файл уже был в git, вы его изменили и сохранили; git заметил разницу, но в коммит файл пока не попадёт | `Changes not staged for commit` | Буква M, имя жёлтое |
| Staged | Вы сделали `git add`: именно эта версия войдёт в следующий коммит. Новый файл после `add` тоже staged (буква A) | `Changes to be committed` | Раздел Staged Changes |

Если после `git add` изменить файл ещё раз, он окажется в обоих разделах (staged и modified).

**Особые случаи:**

- **Deleted** (буква D) — файл был в git, но вы стёрли его из папки; git видит удаление как изменение.
- **Renamed** (буква R) — содержимое то же, имя новое.
- **Ignored** — файл, который git намеренно не замечает (пароли, временные файлы). Задаётся в `.gitignore`, имя серое.
- **C** (conflict) — конфликт при слиянии веток (см. часть 7).

## Часть 5. Первые команды в терминале

### Основной сценарий

```bash
mkdir hello-git && cd hello-git
git init                       # создать репозиторий
# создаём hello.py (для git язык не важен)
git status                     # увидим hello.py как Untracked
git add hello.py               # в индекс
git commit -m "Add hello script"   # сохранить версию
```

### Справочник команд

| Команда | Что делает | Важно |
| --- | --- | --- |
| `git init` | Превращает папку в репозиторий: появляется скрытая `.git` | Один раз при старте проекта с нуля; для скачанного проекта не нужна |
| `git status` | Показывает, какие файлы новые, изменённые, подготовленные | Безопасна, ничего не меняет, вводите как можно чаще. Красным — не подготовлено, зелёным — готово к коммиту |
| `git add файл` | Переносит файл в индекс (staging area) | Не сохраняет версию, сохранение делает только `git commit` |
| `git add .` | Подготавливает все изменённые и новые файлы текущей папки и вложенных | Точка — «текущая папка», без неё не сработает. Сначала посмотрите `git status`, чтобы не добавить лишнее (например, файл с паролем) |
| `git commit -m "текст"` | Сохраняет всё из индекса как новую версию (коммит) | `-m` (message) — короткое описание. Ответ вида `[main 3f2a9c1] ... 1 file changed, 1 insertion(+)` — начало хеша, число изменённых файлов и строк |
| `git diff` | Построчно показывает, что изменилось в ещё не подготовленных файлах | `git diff --staged` — то, что уйдёт в коммит; выход из просмотра — `q` |
| `git log` | История коммитов, новые сверху: хеш, автор, дата, сообщение | `HEAD` («голова») — указатель на то место, где вы сейчас; листать стрелками, выйти `q` |
| `git log --oneline` | История по одной строке на коммит: 7 символов хеша и сообщение | `git log --oneline --graph --all` рисует ветки прямо в терминале |
| `git show хеш` | Один коммит целиком: автор, сообщение, изменения | Хватит первых 7 символов хеша; без параметра покажет последний коммит |

### Как читать diff

```diff
--- a/hello.py
+++ b/hello.py
@@ -1,2 +1,3 @@
 def greet(name):
-    print("Hello, " + name)
+    message = "Hello, " + name
+    print(message + "!")
```

- Строка с `-` (красная) была и удалена; с `+` (зелёная) добавлена; без цвета — не менялась, показана для контекста.
- `@@ -1,2 +1,3 @@` — «в старой версии это строки 1–2, в новой — 1–3».
- Изменённая строка в diff — это «минус старая, плюс новая».

### Хорошее сообщение коммита

- **Плохо:** `fix`, `update`, `asdf`, `готово`, `final_final` — через неделю не поймёте, что это было.
- **Хорошо:** `Add login form`, `Fix crash on empty name`, `Update README with install steps`.
- Правила: начинайте с глагола в повелительном наклонении (Add — «добавить», Fix — «исправить»); пишите коротко, до 50–70 символов; один коммит — одна законченная мысль.

### Файл .gitignore

Есть файлы, которые нельзя или не нужно хранить в истории: пароли, ключи, временные файлы, папки с установленными библиотеками. В корне проекта создают текстовый файл `.gitignore` (с точкой в начале), и git перестаёт предлагать эти файлы к добавлению.

```gitignore
# секреты
.env
# библиотеки
node_modules/
# временное
*.log
__pycache__/
```

`#` начинает комментарий, `*` означает «любые символы» (`*.log` — все файлы `.log`), слэш в конце означает папку.

## Часть 6. Git в VS Code: то же самое кнопками

Слева в VS Code значок **Source Control** (Система управления версиями) — третий сверху. Сверху вниз в панели: поле **Message** для описания коммита, кнопка **Commit**, списки **Staged Changes** и **Changes**, внизу **Graph** (история).

| Шаг | Что делать в VS Code | Эквивалент в терминале |
| --- | --- | --- |
| 1. Создать репозиторий | Открыть папку (File → Open Folder), в Source Control нажать **Initialize Repository**. Нет кнопки — репозиторий уже создан или открыта не та папка | `git init` |
| 2. Подготовить файлы | Навести на файл в Changes и нажать «+» (Stage Changes). «+» у заголовка Changes подготовит все файлы. «−» (Unstage Changes) вернёт файл назад | `git add`, `git add .`, `git restore --staged` |
| 3. Сделать коммит | Вписать сообщение в Message и нажать **Commit** (или `Ctrl+Enter`). В коммит попадёт только содержимое Staged Changes, остальное ждёт следующего коммита | `git commit -m "..."` |
| 4. Посмотреть diff | Щёлкнуть по имени файла в Changes: слева прежняя версия (HEAD), справа ваша (Working Tree). Красное убрано или заменено, зелёное добавлено | `git diff` |
| 5. Отменить правки | Значок со стрелкой назад (Discard Changes). Это нельзя отменить: несохранённые в git правки пропадут навсегда, VS Code переспросит | `git restore файл` |

### Граф истории (Graph)

- Новые коммиты сверху: сообщение, автор, ярлыки веток. Синий ярлык `main` — ветка, на которой вы сейчас.
- Кружок — коммит, линия — связь с предыдущим. Жёлтая линия — отдельная ветка, которая позже влилась в `main`.
- Щёлкните по коммиту, чтобы увидеть изменённые файлы; правая кнопка мыши даёт дополнительные операции.

### Буквы справа от файлов

`U` — новый, `M` — изменён, `A` — добавлен, `D` — удалён. Цвет имени совпадает с буквой.

## Часть 7. Ветки, слияние и конфликты

### Зачем нужны ветки

Если двое правят одну линию истории, они мешают друг другу, а недоделанный код может сломать рабочую программу. **Ветка (branch)** — отдельная линия работы: вы пробуете идею, а основной код (обычно `main`) остаётся нетронутым. Готовую и проверенную функцию вливают в основную ветку, не получилось — ветку удаляют. Аналогия: черновик и чистовик.

Ветка в git — не копия файлов, а **ярлык (указатель) на один коммит**. Когда вы делаете новый коммит, ярлык сам сдвигается вперёд. Создать ветку — значит поставить ещё один ярлык на тот же коммит, это мгновенно. Ярлык `HEAD` показывает, на какой ветке вы стоите.

### Команды для веток

| Команда | Что делает | Важно |
| --- | --- | --- |
| `git branch` | Список веток; звёздочка и зелёный цвет — текущая | Без параметров ничего не создаёт и не меняет |
| `git switch -c feature-login` | Создаёт ветку и сразу переходит на неё (`-c` — create) | Имена латиницей, без пробелов, коротко и по смыслу: `feature-login`, `fix-crash` |
| `git switch main` | Переключает на существующую ветку, файлы в папке меняются на версию этой ветки | Перед переключением сделайте коммит или проверьте `git status`, чтобы не потерять правки |
| `git branch -d feature-login` | Удаляет уже влитую ветку; сами коммиты остаются в истории | Невлитую ветку git не удалит; `-D` (большая D) удаляет принудительно, осторожно |

**В VS Code:** имя текущей ветки в левом нижнем углу (строка состояния); клик по нему открывает список веток. **Create new branch** — создать ветку и перейти на неё, выбор ветки из списка — `git switch`.

### Слияние (merge)

Слияние берёт изменения из одной ветки и добавляет их в ту, на которой вы стоите. Порядок: сначала `git switch main` (ветка, **куда** сливаем), затем `git merge feature-login` (**откуда**).

&#91;embedded content: fast-forward и 3-way merge, до и после\]

- **Fast-forward.** Если в `main` с момента ответвления ничего не добавилось, git не создаёт ничего нового, а «перематывает» ярлык `main` на последний коммит ветки. История остаётся прямой линией.
- **3-way merge.** Если в обеих ветках появились свои коммиты, git сравнивает три точки: общего предка и концы обеих веток, собирает результат и записывает его новым **коммитом слияния** M с двумя родителями.
- Если оба автора правили одно и то же место, git не сможет выбрать сам, и возникнет **конфликт**.

### Конфликты

Конфликт — не поломка, а просьба о помощи: git не знает, чья версия правильна, и не будет выбирать за вас, чтобы не потерять чужую работу. Конфликты случаются в любой команде, бояться их не нужно.

**Шаг 1. Git сообщает о конфликте.**

```bash
$ git merge feature-login
Auto-merging hello.py
CONFLICT (content): Merge conflict in hello.py
Automatic merge failed; fix conflicts and then commit the result.
$ git status
You have unmerged paths.
        both modified:   hello.py
```

`both modified` — изменён с обеих сторон; `unmerged paths` — файлы, которые вы решаете сами. Ничего не потеряно: вернуться можно командой `git merge --abort`.

**Шаг 2. Что git записал в файл.**

```text
def greet(name):
<<<<<<< HEAD
    print("Hello, " + name)
=======
    print("Привет, " + name)
>>>>>>> feature-login
```

- `<<<<<<< HEAD` — начало конфликта, ниже ваш вариант (из ветки, на которой вы стоите).
- `=======` — разделитель.
- `>>>>>>> feature-login` — конец; выше разделителя вариант из вливаемой ветки.

**Шаг 3. Решаем.**

1. Оставьте нужный вариант или соберите свой, удалите все три метки.
2. `git add hello.py` — «я исправил, файл готов».
3. `git commit -m "Merge feature-login"` — создаёт коммит слияния, конфликт решён.

**В VS Code** над конфликтом появляются ссылки: **Accept Current Change** (принять мой вариант), **Accept Incoming Change** (принять чужой), **Accept Both Changes** (оставить оба), Compare Changes. Метки исчезают сами; затем в Source Control выполните Stage («+») и Commit. Цвета: зелёный — ваше, синий — чужое.

### Rebase (перебазирование)

&#91;embedded content: rebase: до и после\]

Rebase «переносит» коммиты ветки так, будто вы начали работу не от старого коммита B, а от самого свежего C. Коммиты пересоздаются с новыми хешами, потом ветку можно влить перемоткой.

> **Золотое правило rebase:** не делайте rebase для коммитов, которые уже отправлены на сервер и которыми пользуются другие. Rebase меняет хеши, то есть переписывает историю: у коллег останутся старые версии, и их история разойдётся с вашей.

Безопасно — на своей локальной ветке, которой ещё никто не пользуется. Если сомневаетесь, используйте merge: он ничего не переписывает.

## Часть 8. Как отменять и откатывать

### Карта отмены: что делать, если...

Идём сверху вниз, от самых безопасных команд к самым опасным.

| Ситуация | Команда |
| --- | --- |
| Испортил файл, ещё не делал add | `git restore файл` |
| Сделал add по ошибке | `git restore --staged файл` |
| Ошибся в последнем коммите | `git commit --amend` |
| Старый коммит надо отменить, он уже отправлен | `git revert хеш` |
| Хочу откатить свою локальную работу | `git reset` |

### Каждая команда отдельно

| Команда | Что делает | Осторожно |
| --- | --- | --- |
| `git restore hello.py` | Возвращает файл к виду из последнего коммита (restore — «восстановить») | Все несохранённые правки в файле пропадают, в корзину они не уходят |
| `git restore --staged hello.py` | Убирает файл из индекса, содержимое остаётся прежним | Опасности нет, правки не пропадают |
| `git commit --amend -m "..."` | Заменяет самый последний коммит: поправить сообщение или добавить забытый файл (сначала `git add`) | Хеш коммита меняется (был `3f2a9c1`, стал `5b8c0de`). Не делайте для коммитов, уже отправленных на сервер |
| `git revert 9c1d4e7` | Создаёт **новый** коммит, отменяющий изменения указанного; старый остаётся в истории | История не переписывается, поэтому безопасно для опубликованных коммитов |
| `git reflog` | Журнал всех перемещений HEAD: коммиты, переключения веток, reset — «чёрный ящик» git | Хранится только на вашем компьютере и несколько недель |
| `git stash` | Прячет незавершённые изменения «в ящик», рабочая папка становится чистой (WIP — work in progress). Удобно, чтобы срочно переключиться на другую ветку | Вернуть: `git stash pop` |
| `git tag v1.0` | Ставит постоянную метку на коммит; в отличие от ветки, тег не двигается. Нужен для релизов: v1.0, v2.1.3 | `git tag` — список тегов |
| `git cherry-pick 8a3c2d1` | Берёт **один** коммит из другой ветки и копирует в текущую, остальные не затрагиваются | Например, срочное исправление сделано не в той ветке. У копии новый хеш |

### git reset: три режима

| Режим | Что происходит |
| --- | --- |
| `--soft` | Сдвигает ветку назад; файлы и индекс не трогает, изменения остаются подготовленными (staged) |
| `--mixed` (по умолчанию) | Сдвигает ветку и очищает индекс; файлы не трогает, изменения остаются в рабочей папке как modified |
| `--hard` | Сдвигает ветку и перезаписывает файлы; все несохранённые изменения пропадают без возврата |

```bash
git reset --soft HEAD~1   # HEAD~1 — «на один коммит назад от текущего»
```

Reset переписывает историю, поэтому используйте его только для локальных, ещё не отправленных коммитов; `--hard` — только если уверены.

**Спасение после ошибки:** даже после `reset --hard` потерянный коммит можно найти в `git reflog` по хешу и вернуться: `git switch -c rescue хеш`.

```bash
git stash                  # спрятать правки
git switch other-branch    # сделать срочное дело
git switch main
git stash pop              # достать правки обратно
```

## Часть 9. Работа с удалённым репозиторием

Локальный репозиторий лежит на одном компьютере: сломается диск — история пропала, а коллегам негде взять ваш код. **Удалённый репозиторий (remote)** — копия проекта на сервере, к которой имеют доступ все участники. У каждого своя полная локальная копия; с сервером обмениваются изменениями: отправляют свои и забирают чужие. По умолчанию удалённый репозиторий называют **origin** («источник»).

&#91;embedded content: цикл работы с удалённым репозиторием\]

Обычный рабочий день: `pull` — получил свежее; поправил файлы; `add` и `commit` — сохранил у себя; `push` — поделился с командой.

### Команды

| Команда | Что делает | Детали |
| --- | --- | --- |
| `git remote add origin https://github.com/ivan/hello-git.git` | Связывает локальный репозиторий с адресом на сервере и даёт ему имя `origin` | Нужна, если проект начат локально через `git init`. После `clone` связь уже создана. `git remote -v` (verbose) показывает все связи |
| `git clone адрес` | Скачивает полную копию репозитория вместе со всей историей и сразу настраивает `origin` | Когда присоединяетесь к существующему проекту или берёте чужой открытый код. Дальше `cd hello-git` |
| `git push -u origin main` | Отправляет новые коммиты на сервер: origin — куда, main — какую ветку | `-u` связывает локальную ветку с серверной, потом достаточно `git push`. Отправляется только закоммиченное |
| `git fetch origin` | Скачивает новые коммиты, но **не** меняет ваши файлы и ветки; вы только узнаёте, что нового | Скачанное лежит в ветке `origin/main`; сравнить: `git log main..origin/main` |
| `git pull` | Скачивает новые коммиты и сразу вливает в текущую ветку | `git pull` = `git fetch` + `git merge`, поэтому возможен конфликт, он решается как раньше |

### Как git узнаёт, что это вы

- **Токен доступа (token)** — длинная строка вместо пароля. Создаётся в настройках GitHub и вставляется, когда git просит пароль. Обычный пароль для git-операций GitHub больше не принимает.
- **SSH-ключ** — пара файлов: открытый ключ вы загружаете на сайт, закрытый хранится у вас. Один раз настроили — пароль больше не нужен.
- Новичкам проще начать с VS Code: при первом push он откроет браузер и попросит войти в GitHub, дальше всё запомнится.
- **Токен и закрытый ключ — это ваш пароль.** Никому не показывайте и не добавляйте в репозиторий.

### Синхронизация в VS Code

После коммита синяя кнопка превращается в **Sync Changes** (синхронизировать) со счётчиком: цифра со стрелкой вверх — сколько коммитов ждут отправки, со стрелкой вниз — сколько можно забрать. Нажатие выполняет pull, а затем push. Если ветки ещё нет на сервере, будет кнопка **Publish Branch** (опубликовать ветку) — это `git push -u`.

## Часть 10. git — это не GitHub

|  | git | GitHub |
| --- | --- | --- |
| Что это | Программа на вашем компьютере | Сайт (сервис, компания) |
| Что делает | Хранит историю изменений, работает без интернета | Хранит копии git-репозиториев в интернете и добавляет удобства для совместной работы |
| Когда создан | 2005, Линус Торвальдс | 2008 |
| Цена | Бесплатный | — |

Гитом можно пользоваться без GitHub, а вот GitHub без git не существует: он построен вокруг него.

**Аналогии:**

- Электронная почта — технология, Gmail, Mail.ru, Яндекс — сайты, которые её предлагают. Так же git — технология, а GitHub, GitLab, Bitbucket — сайты. Сменить сайт можно, git остаётся.
- Word — программа для документов, а Google Drive или OneDrive — места, где их можно хранить и обсуждать.

### Где можно хранить репозитории

| Сервис | Кратко |
| --- | --- |
| GitHub | Самая большая платформа. Принадлежит Microsoft (куплена в 2018 году за 7,5 млрд долларов). Огромное сообщество и открытые проекты |
| GitLab | Основана в 2011 году. Ядро с открытым кодом, можно установить на свой сервер. Сильна встроенными средствами сборки |
| Bitbucket | Сервис компании Atlassian, тесно связан с Jira, часто встречается в корпоративной среде |
| Gitea, Codeberg, Azure DevOps | Первые два — открытые и лёгкие; Azure DevOps — от Microsoft |

Все они работают с одним и тем же git, поэтому проект можно перенести с одного на другой.

## Часть 11. GitHub и GitLab в команде

### GitHub как «соцсеть для программистов»

- **Профиль (profile)** — ваша страница: фото, имя, описание, закреплённые (pinned) репозитории, подписчики (followers), календарь активности (чем зелёнее квадрат-день, тем больше коммитов). Это ваше портфолио, работодатели часто смотрят именно профиль.
- **Социальные функции:** follow (подписка на людей), star («лайк» проекту и закладка), watch (уведомления об изменениях), обсуждения прямо под кодом. Всё общение привязано к коду, поэтому GitHub и называют социальной сетью для программистов.
- **Страница репозитория:** заголовок «владелец / проект» и метка Public/Private; кнопки Star, Fork, Watch; выбор ветки и список файлов с последними сообщениями коммитов; внизу `README.md` — главный текст проекта (что делает, как запустить).

### Публичные и приватные репозитории, лицензии

- **Public** — виден всем, читать и скачивать может любой, менять — только те, кому даны права. Подходит для учебных и открытых проектов.
- **Private** — виден вам и приглашённым. Подходит для коммерческого кода, курсовых до сдачи и всего, что нельзя показывать всем.
- **Лицензия (license)** — файл `LICENSE`, где автор разрешает другим пользоваться кодом. MIT — можно почти всё, нужно сохранить имя автора; GPL — производный код тоже должен остаться открытым. Без лицензии код формально нельзя свободно использовать, даже если он публичный.

### Issues: список задач проекта

**Issue** (задача) — карточка с описанием ошибки или идеи; любой может завести её и обсуждать в комментариях. Метки (labels): `bug` (ошибка), `enhancement` (улучшение), `question` (вопрос). Номер задачи (`#12`) можно упомянуть в коммите, и GitHub свяжет их. Когда ошибка исправлена, задачу закрывают.

### Fork: своя копия чужого проекта

В чужой открытый проект вы не можете просто отправить изменения: права есть только у авторов. **Fork** («развилка») — кнопка на GitHub, создающая вашу личную копию чужого репозитория в вашем аккаунте. В своей копии вы вольны делать что угодно, а потом предлагаете авторам принять изменения через pull request. Так вносят вклад тысячи незнакомых людей, не получая прав на оригинал.

&#91;embedded content: путь изменения через fork и pull request\]

### Pull request (PR)

**Pull request** («запрос на принятие изменений») — просьба к авторам: «заберите мои изменения в свой проект». Pull — «потянуть»: вы просите владельца потянуть ваши изменения к себе. Внутри: заголовок, описание, список изменённых файлов, комментарии и результаты автоматических проверок. PR используют не только для чужих проектов: внутри команды каждая задача идёт через PR, коллеги проверяют код до слияния. В GitLab это называется **merge request** (MR).

**Как открыть PR:**

1. Создайте ветку: `git switch -c fix-readme`.
2. Внесите правки и сделайте коммит: `git add`, `git commit`.
3. Отправьте ветку на сервер: `git push -u origin fix-readme`.
4. На странице репозитория нажмите зёлёную кнопку **Compare & pull request**.
5. Напишите заголовок и описание, нажмите **Create pull request**.

Страница PR: вкладки Conversation (обсуждение), Commits, Files changed (изменённые файлы, строки с `-` и `+`), зелёная плашка «All checks have passed» и кнопка Merge pull request.

### Ревью (code review)

Коллеги читают ваши изменения и пишут замечания до того, как код попадёт в основную ветку. Замечание оставляют на вкладке Files changed: «+» рядом со строкой, комментарий, можно предложить готовую правку. Итог: **Approve**, **Request changes** или **Comment**. Получив замечания, поправьте код в той же ветке, сделайте коммит и push: PR обновится сам. Ревью ловит ошибки, делит знания в команде и держит единый стиль.

### Три способа слить PR

| Способ | Что происходит |
| --- | --- |
| Create a merge commit | Обычное слияние: сохраняет все коммиты и добавляет коммит слияния, история подробная |
| Squash and merge | Склеивает все коммиты PR в один: история чистая, но детали правок теряются |
| Rebase and merge | Переносит коммиты в основную ветку без коммита слияния, линия получается прямой |

Какой выбрать, решает команда; для начала подойдёт любой. Squash и merge commit встречаются чаще всего.

### CI: автоматическая проверка

**CI (continuous integration, «непрерывная интеграция»)** — робот, который при каждом коммите сам проверяет проект: собирается ли программа, проходят ли тесты, нет ли ошибок в стиле кода. Результат — зёлёная галочка или красный крестик прямо в pull request. Ошибку видно сразу, а не после слияния; ревьюер не проверяет то, что может проверить машина. Многие команды разрешают слияние только после зелёной проверки.

Цепочка: push или PR → робот CI скачивает код, собирает, запускает тесты → зелёная галочка или красный крестик в PR. Если тесты упали, журнал с строкой ошибки есть на вкладке Actions или рядом со значком в PR.

**GitHub Actions** — файл `.github/workflows/tests.yml` (формат YAML, настройки записаны отступами): `on` — когда запускать, `runs-on` — на какой системе, `steps` — шаги.

```yaml
name: Tests
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: python -m unittest
```

### GitLab

GitLab — платформа для хранения репозиториев, основана в 2011 году, ядро с открытым кодом (open core). Главное отличие: её можно установить на собственный сервер, код не покидает организацию (так делают многие вузы и компании). Команды git такие же; если вы знаете GitHub, GitLab освоите за день: меняются названия кнопок.

| GitHub | GitLab |
| --- | --- |
| Pull request (PR) | Merge request (MR) |
| Fork | Fork |
| Issues | Issues |
| GitHub Actions | GitLab CI/CD |

В GitLab настройки CI лежат в файле `.gitlab-ci.yml` в корне проекта; проверки выполняют программы **runner** («исполнитель»), они могут стоять на сервере организации.

```yaml
test:
  image: python:3.12
  script:
    - python -m unittest
```

### Роли в проекте

| Роль | Кто это |
| --- | --- |
| Owner (владелец) | Создал репозиторий, полный контроль: настройки, доступ, удаление |
| Maintainer (сопровождающий) | Следит за проектом, принимает pull request, решает, что войдёт |
| Collaborator (участник) | Приглашён владельцем, может отправлять изменения напрямую |
| Contributor (вкладчик) | Тот, кто внёс вклад; часто работает через форк и PR без особых прав |

В списке contributors на странице репозитория показаны все, чьи изменения приняты; попасть туда можно даже с исправлением опечатки.

### Ваш первый вклад в открытый проект

1. Найдите проект, прочитайте `CONTRIBUTING.md` («как вносить вклад») и README.
2. Выберите простую задачу с меткой `good first issue`.
3. Сделайте fork, clone, ветку, правку, commit, push.
4. Откройте pull request, вежливо отвечайте на замечания и дождитесь слияния.

## Часть 12. Как работают команды и что запомнить

### Три схемы работы с ветками

| Схема | Правила | Когда подходит |
| --- | --- | --- |
| **GitHub Flow** (самая простая) | `main` всегда рабочая. Для каждой задачи своя ветка от `main`. Задача готова — открываем pull request, проходим ревью и CI, вливаем в `main`, ветку удаляем | Большинство небольших и средних проектов |
| **Git Flow** (для релизов) | `main` — только выпущенные версии (каждый коммит — релиз с тегом); `develop` — основная ветка разработки; `feature/*` — ветки функций от `develop`; `release` и `hotfix` — подготовка релиза и срочные исправления | Продукты с выпуском версий по расписанию. Схема строгая, для небольших проектов часто избыточна |
| **Trunk-based** (ствол) | Один «ствол» — `main`. Все быстро вливают маленькие изменения, иногда по несколько раз в день. Ветки живут часы или день-два, чтобы не копились конфликты | Команды, которые часто выкладывают обновления. Нужны хорошие автотесты (CI) и дисциплина: недоделанное прячут за переключателем |

### Типичные ошибки новичков

| Ошибка | Как правильно |
| --- | --- |
| Забыли `git add`, коммит пустой | Проверять `git status` перед коммитом |
| Коммиты «fix», «123» | Писать осмысленные сообщения |
| Всё в одном огромном коммите | Коммитить маленькими логическими шагами |
| Пароли и ключи в репозитории | Использовать `.gitignore`; если утекло — сменить пароль |
| Работа прямо в `main` | Делать ветку на каждую задачу |
| Боятся конфликтов, удаляют папку и клонируют заново | Читать сообщение git и решать конфликт по шагам |

### Шпаргалка 1: локальная работа

```bash
git init                  # создать репозиторий
git status                # что изменилось
git add файл              # подготовить файл
git commit -m "…"         # сохранить версию
git diff                  # разница в файлах
git log --oneline         # короткая история
git restore файл          # отменить правки в файле
git switch -c имя         # создать ветку и перейти
git merge ветка           # влить ветку в текущую
```

### Шпаргалка 2: сервер и отмена

```bash
git clone адрес           # скачать репозиторий
git remote -v             # показать связи
git push                  # отправить коммиты
git fetch                 # скачать, не вливая
git pull                  # скачать и влить
git stash / git stash pop # спрятать и вернуть правки
git revert хеш            # отменить коммит новым
git reset --soft HEAD~1   # откатить коммит локально
git reflog                # найти потерянный коммит
```

### Главное, что нужно запомнить

1. git — программа на моем компьютере, GitHub — сайт. Это разные вещи.
2. Файл идёт путём: изменил, подготовил (`add`), сохранил (`commit`).
3. Ветки позволяют работать, не ломая основной код.
4. Командная работа: fork, pull request, ревью, CI.
5. Если страшно — вызывайте `git status` и читайте сообщение git.
